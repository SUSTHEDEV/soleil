Null Operators

Every nullable value must be discharged through one of four notations — or an explicit nil narrow. Table reads are always nullable, so these operators are part of daily life in Soleil.

The four notations

  • T? — a nullable type; sugar for T | nil
  • x?.f / x?.m(args) — safe access: nil short-circuits the access
  • x ?: d — elvis / default: substitutes on nil only
  • x!! — not-null assertion: assumes x is there, throws a named error otherwise
  • if x ~= nil — flow narrowing
notations.sol content_copy 
local name : string? = "Sol"

local a : string? = name          -- still nullable
local b : string  = name ?: "sun" -- discharged with a default
local c : string  = name!!        -- discharged with an assertion

Safe access ?.

?. short-circuits only on its receiver being nil. It extends to indexing t?[k] and method calls a?.m(). A field of type T behind a nullable receiver comes out as T?.

safe.sol content_copy 
class Player(name : string) end

local p : Player? = Player("bob")
local n : string? = p?.name       -- string?
local m : string? = p?.name:sub(1, 1)

Elvis ?:

x ?: d evaluates d only when x is nil — it substitutes on nil only: a false passes through untouched. The result is T | U, collapsing to T when the default's type fits. ?: sits between and and the comparison level, is right-associative, and chains left to right.

elvis.sol content_copy 
local xs : table[number] = { 7 }
local first : number = xs[1] ?: 42   -- table reads are nullable

local flag : boolean? = false
local f : boolean = flag ?: true     -- false! substitution is nil-only

local a : number? = nil
local b : number? = 5
local n : number = a ?: b ?: 7       -- chains

Not-null assertion !!

x!! claims a nullable is present. It compiles to an explicit assertion whose message names the expression — never a raw Lua "attempt to index nil". Applying it to a non-nullable value is a compile error.

assert.sol content_copy 
class P(x : number) end
local p : P? = P(7)

local n : number = p?.x!! + 1  -- assert, then add

Flow narrowing

An explicit nil comparison narrows in both branch directions: if x ~= nil narrows x in the then-block, if x == nil narrows in the else-block — and the complement branch types x as nil, where any use fails loudly. Assignments to the narrowed name inside a branch cancel that branch's shadow, so a stale refinement can never lie about a reassigned value.

narrow.sol content_copy 
local shapes : table[Circle | Square] = { Circle(1), Square(1) }

local s = shapes[1]
if s ~= nil then
    print(s:area())  -- safe: narrowed
end

type() checks refine unions on locals and dotted fields alike: if type(self.v) == "number" refines self.v to its number member in the then-branch and to the complement in the else-branch.

typerefine.sol content_copy 
class P(v : number | string)
    function isnum(self : P) : boolean
        return type(self.v) == "number"
    end
end

Composing them

Precedence: ?. and !! bind tightest as postfix operators; ?: sits between and and the comparison level and is right-associative — so compositions read naturally without parentheses. At codegen, ?. and ?: compile to nil-checked IIFEs, never and/or desugaring (which would be unsound on false).

compose.sol content_copy 
class P(x : number) end
local p : P? = P(6)

local a : number = (p?.x ?: 0) + 1
local b : number = p?.x!! + 1
